# 外部開発会社の検証表 監査結果

更新日：2026-09-13

## 結論

検証表は、不具合候補を集めた探索・結合テストの資料としては有用です。ただし「単体テスト」としては妥当ではなく、記載された OK 数をそのまま品質保証の根拠にはできません。

- 実施内容の中心は Playwright による画面操作、HTTP 応答確認、DB データの投入・変更、ソース確認であり、単体テストではなく結合テストまたは E2E テストです。
- 実装仕様を知らない担当者が、古いテストケースの期待値と現在の実装を比較しているため、仕様変更を不具合として数えたケースがあります。
- 反対に、期待結果が「-」のため HTTP 500 を OK としたケースがあり、重大障害を合格扱いする判定も含まれます。
- 自動結果と手動確認の独立性が弱く、手動確認者は全件同じ担当者です。

したがって、合格率 1320 / 1425（92.6%）は参考値です。製品の合格率としては採用せず、各ケースを現行仕様へ再対応付けしたうえで再集計する必要があります。

## 判定品質の具体的な問題

1. OK再検証のケース299は、実際結果に HTTP 500 と書かれている一方、期待結果が「-」のため OK になっています。期待値未定義のケースは合否判定せず「要仕様確認」にするべきです。
2. 追加OKのケース181は、対象データが status=1 だと画面全体が500になるため status=3へ一時変更して確認し、OKにしています。前提データを回避しているため、元ケースの合格証拠にはなりません。
3. OK再検証167件のうち31件は、期待結果または対象機能が未定義・「-」です。
4. 追加OK 200件のうち、少なくとも27件はソース確認だけ、ブラウザを実際に開いたと明記されたものは50件でした。
5. 104件のNGは管理番号単位で数えていますが、権限テーブル・操作ログ・LIKE旧仕様・稼働宣言など同じ原因が複数画面で重複しています。原因単位の件数と影響画面数を分けるべきです。

## 今後のテスト表の直し方

- 種別を「単体」「API」「結合」「E2E」「ソース確認」に分ける。
- 各ケースに仕様の根拠、事前条件、入力、期待する画面表示・HTTP・DB差分を必須で書く。
- 期待結果が未定義のケースは実行せず、「要仕様確認」にする。
- 不具合は原因ごとに1件とし、影響画面を子項目として記録する。
- テスト用データを途中で変更した場合は別ケースとして扱い、元ケースをOKにしない。
- 自動実行者と受入確認者を分け、重大フローは別担当が再確認する。
- HTTP 500、権限逸脱、金銭状態の不整合は、他の期待値に関係なく自動的にNGとする。

## 検証範囲の限界

今回の再現判定は、検証表の手順・実際結果、現行コード、database/mock_demo.sql の静的照合によるものです。プロジェクト規約によりDB操作は行っていません。実DBを伴う採用・請求・振込、実端末、実ブラウザの全ケース再実行は、開発者がテスト環境へSQLを適用した後に行う必要があります。
